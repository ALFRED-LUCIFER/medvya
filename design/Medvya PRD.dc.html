Product requirements, phase by phase: what ships first, what ships later, and who receives each release

Medvya is a clinic and doctor platform for India and the UAE: front desk, EMR, AI-drafted notes under clinician sign-off, billing, care follow-up, patient portal and, later, hospital integration. This document consolidates every design in this project, the architecture v2 document, the UI/UX master prompt, the gap analysis, the Azure architecture, the build plan and the October 2026 stack plan into nine phases. Every phase ends with a working release handed to a named group of users.

01

Product summary

Problem

Clinics in India and the UAE run on a mix of paper, legacy desktop software (often Oracle-based) and WhatsApp. Doctors spend a large part of each visit typing notes. Receptionists juggle calls, walk-ins and payments on separate tools. Patient history from other hospitals and labs arrives as PDFs and photos and rarely reaches the chart. Owners will not switch systems if they lose old data or must close for a weekend.

Product

One browser-based platform for the whole clinic day: booking and front desk, nurse intake, patient chart, AI-drafted consultation notes the doctor reviews against source evidence and signs, prescriptions, billing and day-end close, results and follow-up tracking, and a patient portal. It starts as a single modular application and grows into multi-clinic SaaS and hospital integration without a rewrite.

Markets and data residency

India (DPDP Act and 2025 Rules, ABHA/ABDM, GST, DLT SMS) and the UAE (NABIDH, Malaffi, Riayati, eClaimLink, Shafafiya, VAT, ADHICS). Separate data planes per country: Azure Central India and UAE North. No patient record is shared across countries by default.

Technology baseline

The source documents propose three different stacks: ASP.NET Core (architecture v2), React + Vite with NestJS on AKS (Build Plan) and Next.js 16 on App Service (October 2026 plan). This PRD adopts the October 2026 plan for the web application and keeps the parts of the other two that the designs depend on. Confirm in ADR-001 during P0.

Deliberately postponed infrastructure

Kubernetes, microservices, Kafka, GraphQL, Elasticsearch and a separate API framework are not used in P0–P5. Redis/BullMQ, AKS and dedicated stamps are introduced only on evidence: queue throughput, node-pool isolation or an enterprise contract (Azure Architecture stages 2–4). A monorepo is how the code is stored; the modular monolith is how it runs. Both apply, with one deployment and one database per country until P7.
08

Release and delivery process

The same five steps close every phase, so each release reaches its recipients in a predictable way.

{{ s.n }} {{ s.t }} {{ s.d }}
ENVIRONMENTSLocal (Docker Compose) → preview per pull request → staging (synthetic data) → production per country. Production deploys only from tagged releases on protected main.
FEATURE FLAGSEvery phase ships behind per-tenant flags. Pilot clinics receive features before general availability; a flag can be turned off without a redeploy.
VERSIONINGR0–R4 are pilot releases (0.x). R5 is v1.0 general availability. Later phases ship as minor versions; database migrations are forward-only and reviewed.
