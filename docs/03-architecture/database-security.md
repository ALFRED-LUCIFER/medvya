# Database roles and row-level security (MDV-P0-008, rebuilt on PostgreSQL in MDV-P0-034)

Who can do what inside a Medvya database. The roles and schema-wide rights are defined in one idempotent script, [`infra/postgres/roles.sql`](../../infra/postgres/roles.sql); rights on single tables that are narrower than their schema's are in [`infra/postgres/table-rights.sql`](../../infra/postgres/table-rights.sql) (MDV-P0-041). Together they are the single source of truth. Row-level security is written by one helper, `RowLevelSecurity.Tenant` (`src/BuildingBlocks/Medvya.BuildingBlocks.Infrastructure`), from a forward-only `TenantRls` migration in each module. Tests: `DatabaseRoleTests`, `TenantIsolationTests`, `MembershipDirectoryTests`, `RowLevelSecurityTests` in `tests/Medvya.IntegrationTests`. Decisions: [ADR-005](../adr/ADR-005-tenant-isolation-rls.md), [ADR-012](../adr/ADR-012-postgres.md).

National-ID encryption (MDV-P0-035) and the masked reporting views (MDV-P0-037) are described below. The hash chain on append-only tables (MDV-P0-036) is described in ADR-006.

## Roles

Every role is `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION` and `NOLOGIN`. A login (an Entra identity in Azure, a password role in development and tests) is created `IN ROLE` one of them.

| Role | Rights | Never |
|---|---|---|
| `medvya_owner` | Owns every module schema and table; runs DDL. Foreign-key checks run as the owner, so it keeps its data rights | Logins. Nobody connects as it |
| `medvya_migrator` | `USAGE, CREATE` on the module schemas; member of `medvya_owner` with `SET` but not `INHERIT`, so `db-migrate` does `SET ROLE medvya_owner` for the length of a migration | Read or write module data in a plain session (`MigratorCanChangeTheSchemaButNotTouchModuleData`) |
| `medvya_app` | Member of every module role below, nothing else | Any DDL, ownership of any object, disabling a policy or trigger |
| `medvya_tenancy` | `SELECT/INSERT/UPDATE` on schema `tenancy`; `DELETE` only on `OperatingHours` and `Closures` (table-rights.sql) | Any other schema; `UPDATE`/`DELETE` on `TenantIndex`; deleting any other tenancy row (memberships, settings history, access reviews) |
| `medvya_identity` | `SELECT/INSERT/UPDATE` on `identity` | `DELETE` (offboarding is a membership status, a session is revoked not removed) |
| `medvya_patients` | `SELECT/INSERT/UPDATE` on `patients`; `DELETE` only on `PayerCoverages` and `Relationships` (a replaced payer or emergency contact); on `DataKeys` only `SELECT`, `INSERT` and `UPDATE` of the wrapping (`WrapKeyId`, `Wrapped`) | Any other schema; deleting a patient, identifier, merge request or MRN counter; deleting a data key or moving it to another tenant or purpose |
| `medvya_billing` | `SELECT/INSERT/UPDATE` on `billing` | `DELETE` (it would restart a legal number series); changing `TR_DocSequences_OnlyMoveForward` (only the owner can) |
| `medvya_scheduling` | `SELECT/INSERT/UPDATE` on `scheduling`; `DELETE` only on `ScheduleSlots`, `SlotHolds` and `ScheduleExceptions` | Any other schema; deleting appointments or visit history; `UPDATE`/`DELETE` on `OutboxTenants`; reporting has no access (appointments hold the SensitiveHealth visit reason) |
| `medvya_notifications` | `SELECT/INSERT/UPDATE` on `notifications` | `DELETE` (attempts are the delivery history); patients and scheduling data |
| `medvya_leads` | `SELECT/INSERT` on `leads` | `UPDATE`, `DELETE` |
| `medvya_audit` | `SELECT/INSERT` on `audit` | `UPDATE`, `DELETE` (the append-only triggers refuse them for every role too, MDV-P0-036) |
| `medvya_platform` | `SELECT/INSERT/UPDATE` on `platform` (the console's team, keys, links, sessions); on `platform.AuditEntries` only `SELECT/INSERT`. Not a member of `medvya_app`: the console host's own login holds this role alone (ADR-014, MDV-P5-040) | Any clinic schema (`TheConsoleLoginCannotReadClinicData`); `DELETE`; changing the audit log (its triggers refuse it for every role too) |
| `medvya_jobs` | `SELECT/INSERT/UPDATE/DELETE` on `hangfire` (job storage) | Any module's data. Hangfire's tables are created by the deploy (as the owner); the app only works in them |
| `medvya_reporting` | `SELECT` on the tenancy tables listed in `table-rights.sql` (none with personal data) and on the masked views in schema `reporting` (MDV-P0-037) | Any write, any DDL, any `patients` table, `audit`, `identity`, `scheduling` (no masked views for them yet); `tenancy.Invitations`, `DoctorLicences`, `DoctorProfiles`, `Profiles`, `SettingsChanges` (MDV-P0-041) |
| Ledger (`tenancy`, `patients`, `audit` roles) | `SELECT` on `ledger.Tables`, `ledger.Chains` and `ledger.Digests`; `INSERT` on `ledger.Chains` (the chain trigger lists a tenant's first row) and, for `audit` only, on `ledger.Digests` (each published digest, MDV-P0-042) | Writing `ledger.Tables` (only migrations do), `UPDATE`/`DELETE` on any ledger table (`Digests` also refuses them by trigger) |

Default privileges (`ALTER DEFAULT PRIVILEGES FOR ROLE medvya_owner IN SCHEMA …`) give every module role its rights on tables and sequences the owner creates later, so a new table never needs a grant. Two exceptions: a new `tenancy` table is not readable by reporting until it is added to the list in `table-rights.sql` (`EveryTenancyTableReportingReadsHoldsNoPersonalData` checks the list against the data classification), and a table that needs narrower rights than its schema gets them in `table-rights.sql`.

## Row-level security

- **Every clinic-owned table** (a `TenantId` column; `tenancy.Tenants` uses `Id`) is `ENABLE`d and `FORCE`d, with four policies (`tenant_select`, `tenant_insert`, `tenant_update`, `tenant_delete`) comparing the tenant column with `nullif(current_setting('medvya.tenant_id', true), '')::uuid`. `FORCE` binds the owner as well. A connection with no tenant matches no row, for reads and writes alike.
- **The tenant is set per connection** by `TenantSessionInterceptor` (`set_config('medvya.tenant_id', …, false)`). Npgsql resets a connection (`DISCARD ALL`) when it returns to the pool, so a pooled connection never carries another tenant (`PooledConnectionsNeverLeakTenantContext`).
- **The one cross-tenant read (facility picker, MDV-P0-012).** A connection that sets `medvya.user_id` and **no** tenant (only `MembershipDirectory` does) sees that user's `Active` memberships and the tenants and facilities they belong to. Only the SELECT and the UPDATE-visibility conditions have this branch, and it applies only while no tenant is set. Every `WITH CHECK` and the DELETE policy are tenant-only, so such a connection writes nothing (`MembershipDirectoryTests`).
- **Tables with a `TenantId` but no policy** are listed in `RowLevelSecurityTests.IdsOnly`: `tenancy.TenantIndex` and `scheduling.OutboxTenants` (tenant ids only, read by jobs that run with no tenant) `identity.Sessions` (looked up by token before a tenant is known) and `ledger.Chains` (which tenant has a hash chain in which table, so the daily digest can read each chain inside its own tenant, MDV-P0-036). The test fails for any other table, so a new table cannot be forgotten.
- **Adding a table** with a tenant column: call `migrationBuilder.Tenant("schema", "Table")` in its migration. **Adding a module:** add its schema and a row to `module_grants` in `roles.sql`, a `TenantRls` migration, and a cross-schema test in `DatabaseRoleTests`.
- **EF query filters stay as layer one**; RLS is layer two. `TheQueryFilterAloneStillHidesOtherTenants` (RLS out of the way) and `RowLevelSecurityHidesOtherTenantsEvenWithQueryFiltersOff` (filter out of the way) prove each alone.

## Order of operations

1. The administrator runs `roles.sql` then `table-rights.sql` (`dotnet run --project tools/db-migrate -- admin "<admin connection>"`; every deploy, idempotent, also covers new modules). For development add `medvya_app=<password> medvya_migrator=<password>` to create password logins.
2. The migrator login runs `db-migrate migrate "<migrator connection>"` (module migrations, the Hangfire tables, then `table-rights.sql` again now that every table exists, all after `SET ROLE medvya_owner`). `roles.sql` re-grants schema-wide rights, so `table-rights.sql` always runs after it; on a fresh database the single-table rights exist from the end of step 2.
3. The application starts as a login that is a member of `medvya_app`. Never as a superuser or the owner.

The integration fixture does exactly this: `roles.sql` and `table-rights.sql` as the container superuser, migrations as `medvya_migrator`, the administrator step once more (as the next deploy would, so a re-run cannot widen single-table rights), and every context as `medvya_app`. A migration that needs more than the owner role fails the whole suite; an application query that needs more than the module roles fails the test that runs it.

## National-ID encryption (MDV-P0-035)

- **What:** `patients.Identifiers.LookupValue` and `DisplayValue` and `patients.PayerCoverages.MemberNumber` hold AES-256-GCM ciphertext (`bytea`). The associated data is the tenant id plus the value's column and row id (format version 2, MDV-P0-041), so ciphertext pasted into another row, column or tenant does not decrypt (`ACiphertextCopiedIntoAnotherRowDoesNotDecrypt`); a row id never changes (a merge moves an identifier by `PatientId`, not by copying it). `Identifiers.LookupIndex` is an HMAC-SHA-256 blind index (separate per-tenant secret) used for exact-match search and the duplicate check. A database administrator sees bytes only (`AnAdministratorWithoutTheKeySeesOnlyCiphertext`); a pattern search finds nothing (`ALikeSearchOnAnEncryptedColumnIsRejected`).
- **Keys:** each tenant has a data key and a blind-index key, stored only wrapped, in `patients.DataKeys` (forced RLS). The module role cannot delete a key row or re-key it to another tenant or purpose, only re-wrap it. If a key row is gone while the tenant still has encrypted values, the key is refused (`KeyProtectionException.KeyMissing`), never silently replaced by a new key that could not read them (`AMissingKeyForATenantWithEncryptedRowsThrowsAndCreatesNoKey`); restore the row from backup. The wrapping key is a Key Vault key (`NationalIdProtection:KeyVaultKeyId`), usable only by the API identity; Development uses a per-machine key in local application data instead (never in the repository), and no other environment starts without Key Vault. Unwrapped keys stay in memory for five minutes. Library and tests: `src/BuildingBlocks/Medvya.BuildingBlocks.Security`, `tests/Medvya.SecurityTests`.
- **Where:** `NationalIdColumns` (Patients.Infrastructure) encrypts on insert and decrypts on load, with each row's own `TenantId`. It is not an EF value converter, because EF caches one model per context type and a converter would keep the first context's tenant. `PatientsDbContext` cannot be built without it.
- **Destructive migration gate:** `NationalIdEncryption` drops the old plaintext columns, so it refuses to run once `Identifiers` or `PayerCoverages` has ever held a row (`TheNationalIdMigrationRefusesADatabaseThatAlreadyHoldsIdentifiers`). It checks table size, not a row count, because forced row-level security hides every row from the migrator.
- **Limits:** a value is never searchable except by exact match. Seeding outside Development needs Key Vault. shortcut: there is no scheduled re-wrap job yet (`TenantKeyRing.Rewrap` exists and is tested); add it with the Key Vault rotation policy (MDV-P0-038).

## Masked reporting views (MDV-P0-037)

Support and reporting read schema `reporting` only: `reporting."Patients"` (MRN, country, initials, a ten-year age band, sex at birth, status, registration time) and `reporting."Identifiers"` (scheme and value length). No name, date of birth, contact, address or identifier value is in any view, and every `patients` table is denied to the role (`ReportingSeesMaskedDemographicsWhileTheAppSeesClearValues`, `ReportingRoleIsReadOnly`). The views are owned by `medvya_owner` and the base tables `FORCE` row-level security, so a reporting session still needs a tenant and sees only that tenant. A new view goes into schema `reporting` in its module's migration; the default privileges grant it.

## Mapping to Azure (MDV-P0-038, MDV-P0-042)

No password exists anywhere: the server is Entra-only, and every connection to an Azure host without a password signs in with an Entra access token (`PostgresDataSources`, refreshed in the background). The server is private, so nothing outside the VNet connects to it.

- **Deploy job** (`job-db-<env>-<suffix>`, Container Apps in `snet-jobs`, started by `.github/workflows/deploy-dev.yml`). It holds two managed identities. `id-dbadmin-*` is a second Entra administrator of the server. It runs `roles.sql` (`db-migrate admin`) and makes the logins (`db-migrate entra`: `pgaadauth_create_principal_with_oid`, then `GRANT medvya_<role>`). `id-migrate-*` is a login `IN ROLE medvya_migrator` and runs `db-migrate migrate`. The job is manual-trigger only and never retries a failed run.
- **App:** the App Service managed identity is a login named after the app (`app-medvya-<env>-<suffix>`) `IN ROLE medvya_app` (`ConnectionStrings__Medvya` names it as the user, `SslMode=VerifyFull`).
- **Reporting** users are mapped `IN ROLE medvya_reporting` with the same `entra` command, run by an administrator.
- **Human administrator** (`dbAdminObjectId`): for break-glass and the restore drill only. It is not used by any deploy.

## Known limits

- **Accepted limit (for the external review, MDV-P1-038): the tenant and user settings are user-settable.** `medvya.tenant_id` and `medvya.user_id` are ordinary custom settings: any session can `set_config` them to any value. RLS therefore protects against application bugs and injected statements that stay inside the app's own queries, not against someone who can run arbitrary SQL as an app or reporting login (they can pick any tenant). Who may hold such a login: the **app login** only the API's managed identity (no person, no password); the **migrator** only the deploy identity; a **reporting login** only named support staff on a just-in-time Entra group, whose statements pgaudit logs (`infra/bicep/postgres.bicep`); nobody else. Making the tenant unforgeable (a signed token checked by a security-definer function) is the upgrade if a person ever needs a standing app or reporting login.
- The migrator can `SET ROLE medvya_owner` and then read data; the split removes standing access, not the ability. The deploy identity is used only by the deploy job.
- One app login holds every module role, as the app is one process. The module roles still make cross-schema access a deliberate grant, and allow separate logins per worker later.
- Reception-board reads (`front_desk.board.read`) and live-update watches (`front_desk.board.watch`) are audited once per user, tenant and exact request (facility) per 5-minute window (`AuditWindow`, MDV-P1-035). The window is per API instance memory, so a restart or a second instance writes one extra row per window; move it into the database before running more than one instance.
- `reporting` has no audit, identity or scheduling access: they have no masked views yet (audit `ClientIp`, staff contacts, the visit reason).
