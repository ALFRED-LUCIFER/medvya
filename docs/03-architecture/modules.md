# Module boundaries (modular monolith)

Sources: Software Architecture §4, PRD v2 §07 repository, Foundations ERD coverage. Each module owns its schema in Azure SQL (`[patients].[Patient]` etc.) and exposes contracts. Cross-module reads go through application queries or events. **Never** through another module's EF DbContext.

**Scheduling decisions (MDV-P1-011).**

- SCHEDULE_TEMPLATE lives in Scheduling, not Practice. Booking must check "is this doctor working then?" inside the same serializable transaction that writes the appointment, which only works if the template is in the same database context. Practice settings (MDV-P1-005) edit templates through `IScheduleService`.
- Bookable slots are **generated on the fly** from the template for each facility-local day (`ScheduleRules.Day`). Free slots are not stored. Times are wall-clock times in the facility zone; instants are UTC. A wall-clock time in a daylight-saving gap moves later by the gap, and an ambiguous time takes the earlier instant (the java.time rules).
- **No double booking (MDV-P1-022):** every hold and booking runs in `DoctorDayTransaction`: a SERIALIZABLE transaction that first takes `sp_getapplock` on `doctor:{calendar}:{facility-local date}`, then re-checks the template and existing appointments. A booking writes one SCHEDULE_SLOT row per 5-minute unit it occupies, under a unique index on (calendar, location, slot start), so the database refuses any overlap even if the lock or checks are bypassed. Deadlocks and lock timeouts are retried (three attempts, then "busy"). Template times must be on 5-minute boundaries.
- A calendar column is a doctor (an active doctor membership, through Tenancy's `IFacilityDirectory`) or a SCHEDULE_RESOURCE such as a procedure room. Until LOCATION exists (MDV-P1-005), the location is the facility.

Cross-cutting backend-only tables: `OUTBOX_EVENT` (domain events → Service Bus/Hangfire) and Hangfire's job storage (separate schema).
