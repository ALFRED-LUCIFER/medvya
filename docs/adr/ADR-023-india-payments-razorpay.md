# ADR-023 · India payments with Razorpay: each clinic's own account, payment links, paid only after Razorpay confirms

- **Status:** Proposed 16 Nov 2026. Part 2 (webhook, Settings, Billing, Razorpay) built 17 Nov 2026; the keys are not tried against Razorpay when saved (a wrong key shows as "provider_unauthorized" on the first link). The owner decided the account model (each clinic's own Razorpay account, Medvya is not an aggregator) on 16 Nov 2026; the rest needs the owner's agreement. Ticket: MDV-P4-007.
- **Builds on:** [ADR-012](ADR-012-postgres.md) (tenant isolation), [ADR-003](ADR-003-country-isolation.md) (country data stays in country), [ADR-019](ADR-019-subscription-pricing.md) §8 (Medvya's own subscription collection is a separate, later use of the same adapter, MDV-P5-065).

## Context

A clinic in India wants a patient to pay a bill by UPI or card on their phone, and the bill to show Paid only when the money has really arrived. Razorpay is the provider for India (owner decision 16 Nov 2026; test mode first, live keys wait on the merchant account, MDV-P4-032 #489). The money must go straight to the clinic.

## Decision

1. **Each clinic connects its own Razorpay account.** Payments settle into the clinic's account. Medvya never holds or routes the money: it is not a payment aggregator and does not use Razorpay Route. Going live needs each clinic's own Razorpay KYC; Medvya's own merchant path for subscriptions is MDV-P4-032 (#489).
2. **First step (built now): the clinic pastes its keys.** The clinic admin enters the key id, key secret and webhook secret once in Settings → Billing → Razorpay (part 2 of MDV-P4-007). It works in test mode today, with no approval from Razorpay. The screen then shows only "Connected · Test key …1234". The mode is read from the key id (`rzp_test_…` or `rzp_live_…`), never stored apart from it.
3. **Target: Razorpay Technology Partner OAuth.** A "Connect Razorpay" button: the clinic signs in to (or creates) its own Razorpay account and authorises Medvya; Medvya then calls the APIs with a Bearer access token and creates the clinic's webhook by API. The money still goes to the clinic. This needs Medvya approved as a Razorpay technology partner (an owner step, listed in `docs/05-delivery/session-handoff.md`), and Medvya must handle `account.app.authorization_revoked` ([Partners](https://razorpay.com/docs/api/partners/), [partner OAuth webhooks](https://razorpay.com/docs/webhooks/partners/oauth/)). The adapter builds the `Authorization` header in one method, so a Bearer token replaces Basic auth there without touching callers. Not built now.
4. **Standard Payment Links, not UPI-only links or QR codes, for now.** `POST /v1/payment_links/` with Basic auth `key_id:key_secret` ([create](https://razorpay.com/docs/api/payments/payment-links/create-standard/), [authentication](https://razorpay.com/docs/api/authentication/)): `amount` in paise, `currency`, a `reference_id` unique per attempt (40 characters at most; not the invoice number alone, a retry needs a new one), a `description` with no clinical data ("Bill INV/26-27/00342, Sunrise Clinic"), `notify.sms` and `notify.email` false (the clinic sends the link itself), `expire_by` at least 15 minutes ahead (from `BillingSettings.PaymentLinkExpiryMinutes`), and `notes` with opaque ids only. No `customer` block: Razorpay does not need the patient's name or number from us. UPI-only links ([create-upi](https://razorpay.com/docs/api/payments/payment-links/create-upi/)) do not work in test mode, and QR codes need separate activation on each account; both can be added later behind the same contract. Fetch: `GET /v1/payment_links/:id` ([fetch](https://razorpay.com/docs/api/payments/payment-links/fetch-id-standard/)); cancel: `POST /v1/payment_links/:id/cancel`, only while `created` ([cancel](https://razorpay.com/docs/api/payments/payment-links/cancel-standard/)). A refused cancel is answered with the link's current status.
5. **Paid only after a verified webhook or an API fetch shows it.** Webhook delivery is at least once, unordered, and retried for 24 hours ([best practices](https://razorpay.com/docs/webhooks/best-practices/), [payment link payloads](https://razorpay.com/docs/webhooks/payloads/payment-links/)). So a webhook is only a prompt: on every verified event Medvya fetches the link again and acts on its status. A stuck pending payment has a "Check status" action that does the same fetch.
6. **Webhook checks, in this order.** One URL per clinic, `/v1/webhooks/razorpay/{webhookKey}` (the API's own path style; the clinic copies the full URL from Settings, Billing, Razorpay), where `webhookKey` is 64 random hex characters (not the tenant id) that picks the clinic and so its webhook secret; the key proves nothing on its own. The endpoint is explicitly public. `X-Razorpay-Signature` must equal the hex HMAC-SHA256 of the raw body bytes under that clinic's webhook secret, compared in constant time, before the body is parsed ([validate](https://razorpay.com/docs/webhooks/validate-test/)); a mismatch is refused and audited. Events are de-duplicated by the `x-razorpay-event-id` header (a `ProviderEvent` row unique per clinic, provider and event id, MDV-P4-007 part 2), so a replayed event changes state once. The row is written only after the link was fetched and acted on: if Razorpay cannot be reached the endpoint answers 503 and Razorpay's retry tries again. An unknown key is 404 before anything else is read; the body is capped at 64 KB; the endpoint is rate limited per address (`RateLimiting:PaymentWebhooksPerMinute`, default 120), because an unknown key reads the payments Key Vault. The webhook runs in the key's clinic (the same tenant-bound scope as other public links, so row-level security applies) and is not behind the billing flag: a link paid while billing was on still settles after it is turned off. Turning on the Razorpay link payment method needs a connected account (checked on the server).
7. **Secrets per clinic live in a payments Key Vault, never in the database or logs.** The API writes them when the clinic connects, so the app identity needs "Key Vault Secrets Officer". On the main vault that role would let the app read and change every platform secret, so clinic keys get a vault of their own (`kvp-<name>` in `infra/bicep/main.bicep`, the app's role on that vault only, app setting `Razorpay__KeyVaultUri`). Secret names: `razorpay-<tenantId>` holds the key id, key secret, webhook secret and webhook key as JSON; `razorpay-hook-<webhookKey>` holds the tenant id, so a webhook finds its clinic without the database. Reads are cached for five minutes per instance, so webhooks do not call Key Vault each time.
8. **Development uses test keys from user secrets.** Without `Razorpay:KeyVaultUri`, Development reads `Razorpay:Tenants:<tenantId>:KeyId`, `:KeySecret`, `:WebhookSecret` and `:WebhookKey` (64 lowercase hex characters), for example `dotnet user-secrets set "Razorpay:Tenants:<tenantId>:KeySecret" "<test secret>" --project src/Host.Api`. Outside Development without the vault, the store refuses to start (fails closed).
9. **What is never stored or logged.** Never logged: the key secret, the webhook secret, the signature header, the raw webhook body, request bodies (description, notes) or Razorpay's error text, and the customer's VPA, email or phone number. Logs carry the operation and HTTP status only (`LoggerMessage`). Exceptions carry the error kind and HTTP status only. No card number, CVV or UPI PIN ever reaches Medvya (Razorpay's hosted page). A payment stores the link id, payment id, method name, amount and status, nothing more.
10. **A plain typed `HttpClient`, no SDK.** The Razorpay NuGet package (3.3.2) is synchronous (`HttpWebRequest`). Base address `https://api.razorpay.com/v1/`, JSON in snake case, a 10-second timeout. A GET is retried once on a timeout, 429 or 5xx; a POST is never retried, so a create cannot make two links. Errors map to `PaymentProviderError` (NotConnected, Unauthorized, Rejected, Unavailable).

## Test mode facts

30 payment links per business in test mode. Test UPI ids `success@razorpay` and `failure@razorpay`; test cards 4100 2800 0000 1007 (success) and 4100 2800 0006 0003 (declined) ([test cards](https://razorpay.com/docs/payments/payments/test-card-details/), [test UPI](https://razorpay.com/docs/payments/payments/test-upi-details/)).

## Not chosen

- **Medvya as aggregator, or Razorpay Route:** Medvya would hold clinic money and need payment-aggregator licensing. Owner decision against.
- **The official Razorpay .NET SDK:** synchronous, would block request threads.
- **Clinic secrets in the database (even encrypted):** a database read would then reach a key that moves money; Key Vault keeps them out of backups and queries.
- **Write access on the main vault:** too wide (see 7).

## Consequences

- Infrastructure: the payments vault and its role exist only after the owner applies `infra/bicep/main.bicep` (the `infra` workflow, `.github/workflows/infra.yml`); deploys do not re-apply Bicep.
- Each clinic does its own Razorpay KYC before live payments, and copies its webhook URL and secret into its Razorpay dashboard until partner OAuth (3) creates the webhook by API.
- MDV-P4-008 (UAE) implements the same `IPaymentLinks` contract.
